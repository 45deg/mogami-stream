# イベントループへ処理を譲る

同期処理が長く続くパイプラインでは、`tap` のコールバックで待機すると、タイマーやタイマー起点のキャンセルを進められます。以下は既存の演算子を使ったアプリケーション側のヘルパーです。Mogami の既定動作に yield は追加しません。

各ヘルパーと一緒に、`mogami-stream` から `defer`、`from`、`tap` を import してください。

## キャンセル可能な待機

`await Promise.resolve()` が処理を譲る先は microtask です。遅延ゼロのタイマーを使うと、ホストがタイマーや I/O を処理できます。待機が終わると、タイマーと abort listener を解放します。

## 一定件数ごとに処理を譲る

<<< @/examples/event-loop.mjs#count{js}

```js
import { filter, range } from "mogami-stream";

const controller = new AbortController();
await range(0, 100_000)
  .pipe(
    yieldEvery(1_024),
    filter((value) => value % 2 === 0),
  )
  .forEach((value) => console.log(value), { signal: controller.signal });
```

`tap` はコールバックを逐次 await し、Promise を値として持つ要素もそのまま渡します。index は実行ごとにゼロから始まるため、同じ演算子を再利用できます。N 番目の要素を上流から読み取ってから待機し、その後で下流へ渡します。バックグラウンドの読み取りや追加のキューは作らず、下流が読み取らない間はタイマーも作りません。上流に設定した並行数・容量の制限は引き続き適用されます。

ほぼすべての要素を捨てる `filter` など、大量に読み取っても出力しない可能性がある段より前に配置してください。1,024 件の軽い処理と重い処理では占有時間が異なるため、コールバックのコストに合わせて件数を調整します。

## 経過時間で処理を譲る

単調増加時計が処理中も進むホストでは、要素ごとに経過時間を調べる方法も使えます。`defer` の内側で時刻を持つことで、実行ごとの状態を分離します。

<<< @/examples/event-loop.mjs#time{js}

`yieldEvery(1_024)` の代わりに `yieldAfter(4)` を使います。前回の yield 後の上流処理時間と下流の待機時間を含めて判定します。この段に要素が到着したときにしか確認しないため、1 回の重いコールバックで指定時間を超えることがあります。Cloudflare Workers では I/O 後にしか `performance.now()` が進まない場合があるため、件数方式を使ってください。時間判定だけでは一度も yield しない可能性があります。

## 間隔の選び方

遅延ゼロのタイマーでもホストが最小待機時間を設ける場合があり、毎要素の待機は高コストです。同期 map を含む 1 万件の Node.js での探索的な測定では、1,024 件ごとの待機で最初のタイマーまでの遅延が 16.94 ms から 1.88 ms に減り、全体の処理時間は 16.91 ms から 29.56 ms に増えました。専用演算子の試作に、このレシピを上回る結果は得られませんでした。[測定条件と生データ](https://github.com/45deg/mogami-stream/blob/main/benchmarks/event-loop.md)も参照してください。

件数や時間は調整用の目安であり、期限やフレームレートを保証しません。実行中の同期コールバックを中断することはできないため、重い処理は小さな単位に分けてください。ソースやコールバックがすでに I/O を await している場合は、待機を追加する前に測定してください。
