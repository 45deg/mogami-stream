# 複数実行でリクエストの制限を共有する

複数の実行や再試行（retry）をまたいでリクエストの開始間隔を制限するには、1つのリミッタを作成し、[`map`](../operators.md#operator-map) のコールバック内で `limiter.run` を呼び出します。

この2つの実行では開始間隔を最低 100 ms、待機中の呼び出しを最大8件に制限します。

`processJob` は呼び出されたら直ちに I/O を開始し、その I/O に `signal` を渡してください。リミッタは開始時刻の間隔を制御するものであり、先行する I/O の完了を待たずに次の呼び出しを許可します。各実行で同時に進行する項目数は、それぞれの [`map`](../operators.md#operator-map) の `concurrency` で制限されます。

## 待機列とキャンセル

- 待機列は到着順（FIFO）です。再試行は末尾に追加され、他の実行より優先されることはありません。待機中にキャンセルされた呼び出しを取り除いても、残りの順序は保たれます。
- `maxWaiting` は許可待ちの呼び出し数の上限であり、許可済みの1件や実行中の I/O は含みません。上限を超えると `LimiterQueueFullError` で失敗します（この例では再試行対象から除外しています）。`0` を指定すると、即座に開始できる呼び出しだけを許可します。
- バースト用の枠は蓄積されません。最初の呼び出しは直ちに開始できますが、空き時間やタイマーの遅延があった後でもまとめて開始することはありません。経過時間は `performance.now()` で計測し、タイマー発火時にも再確認します。
- 待機中にキャンセルされると `signal.reason` で reject し、abort リスナーを解除して待機枠を解放します（許可枠は消費しません）。許可が下りた後も処理関数を呼ぶ直前にキャンセルを再確認しますが、いったん消費した許可枠はキャンセルや処理失敗時にも返却されません。
- 待機列が空になるとタイマーは残らず、許可済みの呼び出しからは待機用の abort リスナーも解除されます。開始後の I/O の中断は渡された `signal` の処理に従います。

`intervalMs` には正の有限値、`maxWaiting` には 0 以上の安全な整数を指定します。状態はメモリ上で同じリミッタのインスタンスを参照する呼び出し間でのみ共有されるため、別プロセスや Worker スレッド間で制限を共有する場合は外部の仕組みを併用してください。

外部サービスが呼び出し全体で一定の開始間隔を求める場合はこのリミッタを使い、単一実行の上流読み取りペースだけを制限する場合は [`rateLimit`](../guide/timing.md) を使ってください。再試行の設定は[リトライ](../guide/errors.md#retry)を参照してください。
