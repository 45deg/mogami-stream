# fork でソースを共有する

`fork(source, { branches, capacity })` は、1 回のソース実行から、参加中のすべての分岐に同じ値を入力順で配信します。`mogami-stream` と `mogami-stream/core` の両方から利用できます。

どれか 1 つの終了を待つ前に、すべての消費者を開始してください。分岐はイテレータを取得する前から参加しており、キューが満杯になるとソースの新しい読み取りを止めます。`take(0)` やセットアップの失敗で消費が始まらない場合も含め、使わない分岐は必ず離脱させてください。兄弟分岐の進行を待つ間に、その分岐が必要とする共有ロックやワーカー枠を保持してはいけません。

## 容量と所有権

`branches`、`capacity`、その積は正の安全な整数である必要があります。不正な値はソース取得前に `RangeError` になります。生成時にはソースを取得せず、分岐からの最初の要求で読み取りを開始します。分岐ごとのキュー内の値と読み取り予約の合計は `capacity` 以下で、実行中のソース読み取りは全体で最大 1 件です。兄弟分岐が満杯でも、既存のキューからは読み取れます。要求がない間は先読みしません。

Promise を値として持つ場合も含め、複製も `await` もせず同じ参照を配信します。共有する値は変更しないでください。容量は項目数を数え、バイト数や下流の副作用は含みません。チャンクのサイズ、下流の並行数、収集結果にも別の上限を設けてください。

各分岐のイテレータ取得は `iterate()` または `[Symbol.asyncIterator]()` による 1 回限りです。2 回目の取得は `TypeError` を投げ、重複する `next()` は `TypeError` で拒否されます。`from(branch)` でオペレータを使えるようになりますが、分岐を再利用できるようにはなりません。ソースのイテレータはグループが排他的に所有するため、別の場所で消費しないでください。

## 離脱とキャンセル

- `branch.detach()`、イテレータの `return()`、`for await` の `break` は、その分岐を即座に解放します。兄弟分岐は継続します。
- `branch.cancel(reason)` または `iterate({ signal })` は、その分岐だけをキャンセルします。保留中または次の読み取りが 1 回だけ拒否され、以降は終了を返します。
- イテレータの `throw(error)` は、その分岐を失敗させ、即座に拒否されます。ソースに `throw` を転送しません。
- 最後の分岐が離脱すると、グループがソースを停止します。最後の分岐が失敗またはキャンセルされた場合は、その理由でソースをキャンセルします。
- `group.cancel(reason)` またはグループのシグナルは、クリーンアップを待つ前に参加中の全分岐をキャンセルします。`group.close()` は全分岐を離脱させ、クリーンアップを待ちます。

既に中止されたシグナルや最初の読み取り前の停止では、ソースを取得しません。終了操作は冪等です。キャンセルだけでは下流の副作用を中断できないため、一緒に停止させる場合は消費者とその I/O にも共通のシグナルを渡してください。

## 終了レポート

`branch.closed` とそのイテレータの `closed` は、兄弟分岐、下流のコールバック、共有ソースのクリーンアップを待たずに、分岐の終了を報告します。EOF 後はキューの値を配信し、空になった分岐から独立して終了します。ソースの読み取りやクリーンアップが失敗すると、参加中の分岐が失敗してキューを破棄します。既に完了したレポートは変更しません。

`group.closed` は、全分岐、実行中のソース処理、ソースのクリーンアップを待ちます。`group.close()` も同じレポートの Promise を返します。どちらも拒否されません。全消費者が成功した場合も `report.source` を確認してください。分岐終了後に共有クリーンアップが失敗することがあります。`report.branches` は作成順で、下流の副作用ではなく分岐自体の結果を表します。主原因と追加の失敗は[クリーンアップエラーの規則](./errors.md#cleanup-errors)に従います。

終了の Promise を待つだけでは停止しません。EOF 後も未読のキューがあると `group.closed` は保留されます。キャンセルに応じないソース処理がある場合も、離脱済みの分岐は終了しますが、グループは待ち続けることがあります。ソースのファイナライザ内で `group.closed` を待ってはいけません。グループ自身がそのファイナライザを待っているためです。

ハブは読み取りが続くと定期的にイベントループへ処理を譲り、タイマーや中止ハンドラを実行できるようにします。ただし、消費者も共有資源を解放して処理を進める必要があります。キューを大きくしても循環待ちは解消しません。下流の処理については[イベントループへ処理を譲るレシピ](../recipes/event-loop.md)を参照してください。
