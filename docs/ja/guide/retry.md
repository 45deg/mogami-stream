# リトライ

`map` と `mapSettled` の `retry` オプションで、失敗した項目だけを再試行できます。

<<< @/examples/retry.ts

`retries: 3` は初回を含めて最大4回の試行です。`shouldRetry` で再試行するエラーを選び、`delayMs` で待機時間を指定します。上の例では失敗した試行番号に応じて 200・400・800 ms 待ちます。

各試行で項目の `index` は変わらず、`attempt` は1から増えます。`shouldRetry` は同期・非同期の判定に対応し、`false` を返すと再試行を打ち切ります。`delayMs` は固定のミリ秒数でも指定できます。

## 並行数・キャンセル・レート制限

再試行の判定とバックオフ中も、その項目は同じ並行スロットを使用します。キャンセルは待機を中断し、上流の読み取りエラーや後処理のエラーは再試行しません。

上流に置いた `rateLimit` は、失敗や完了確認を含む上流の読み取り回数を実行ごとに制限します。`map` 内部の再試行や、別の実行との合算には対応しません。外部呼び出しの各試行で共通の制限を守るには、処理関数の中で共有のレートリミッタを使います。

## 複数実行でリクエストの制限を共有する

次のアプリケーション用レシピは、処理の開始間隔を一定以上に保ちます。同じ制限を適用する実行間で、1つのリミッタを共有してください。再試行のたびに `limiter.run` を呼ぶため、retryも同じ待機列に入ります。

<<< @/examples/shared-rate-limiter.ts#usage

この2つの実行では、開始間隔を最低100 ms、待機する呼び出しを最大8件に制限します。`processJob` は呼び出されたら直ちに I/O を開始し、その I/O に `signal` を渡してください。リミッタは開始時刻を制御し、先の I/O の完了を待たずに次の呼び出しを許可します。実行ごとの処理中の項目数は、それぞれの `map` の並行数で制限します。

### リミッタの契約

- 待機列は到着順のFIFOです。retryは末尾に入り、別の実行より優先されません。キャンセルした呼び出しを除いても、残りの順序は変わりません。
- `maxWaiting` は許可待ちの呼び出し数の上限で、許可済みの1件や処理中の I/O を含みません。超過すると `LimiterQueueFullError` で拒否し、この例では再試行しません。0の場合は、即座に開始できる呼び出しだけを許可します。
- バースト用の枠は蓄積しません。最初の呼び出しは直ちに開始できますが、長い空き時間やタイマーの遅延後にもまとめて開始しません。間隔は `performance.now()` で測り、タイマー発火時に再確認します。
- 待機中のキャンセルは `signal.reason` で拒否し、listenerを解除して待機枠を空けます。permitは消費しません。許可後も処理関数を呼ぶ直前にキャンセルを再確認します。許可済みのpermitは返却せず、処理に失敗した場合も同様です。
- 待機列が空になるとタイマーは残らず、許可済みの呼び出しには待機用のabort listenerも残りません。開始済み I/O の停止は、その I/O 側のsignal対応に従います。

<<< @/examples/shared-rate-limiter.ts#limiter

`intervalMs` は正の有限値、`maxWaiting` は0以上の安全な整数を指定します。このリミッタはアプリケーション側の実装であり、`mogami-stream` のexportではありません。同じJavaScript realm内で同じインスタンスを使う呼び出しだけが状態を共有します。別プロセスやworker間の制御には、別途共有の仕組みが必要です。

### APIの採否

今回は、テストで検証する利用レシピを採用します。待機列・キャンセル・バーストを許可しない方針を明示し、ストリームのAPIを汎用のリクエストスケジューラへ広げずに利用できます。組み込みにする場合は、サービスごとの時間窓、バースト予算、共有状態の管理主体も決める必要があります。実行ごとの上流read制限には既存の `rateLimit` を使い、外部サービスの制限にこの開始間隔の方針が合う場合にレシピを利用してください。

## 再試行後も失敗した場合

`map` は最後のエラーで実行を停止します。`mapSettled` は失敗を `{ status: "rejected", reason }` として出力し、他の項目の処理を続けます。上流の失敗やキャンセルは、どちらの場合も実行を停止します。
